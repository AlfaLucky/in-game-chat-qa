How the chat works

The screenshot shows the interface in one state. The test cases use the assumptions below. Each rule links to a detail from the mockup and a question to resolve.

R01 Opening and closing chat

Chat opens on the Café the first time. On subsequent visits, it returns to the last tab the player can access. The window’s close button hides chat. Closing a private tab removes the tab, and the conversation history is available when it is reopened.

Closing the active conversation switches chat to the Café. If the last tab is no longer accessible, reopening chat also takes the player to the Café. A click inside chat must not activate a game object underneath it.

R02 Who can see messages

Members of a public channel can see its messages. Only the two participants in a private conversation receive its history and new messages. The server checks access when a player reads history or sends a message.

Each tab has its own messages and draft. A response for a previously selected tab must not replace the current feed. When channel access is revoked, the old feed is hidden and the player can no longer send to that channel.

R03 Unread messages and online count

Assume the red dot means a new message arrived and the player has not seen it yet. It clears when the last unread message is in view. A player’s own messages do not trigger the dot.

For testing, assume the Café counts players once, even if they open the game on two devices. When offline, the count is marked as stale or unavailable. It refreshes after reconnecting.

Mockup M01   Questions Q03 Q04

R04 Message order and scrolling

After syncing, the feed follows the order set by the server. Receiving the same event twice does not add a second copy of the message. The client displays server timestamps in the player’s time zone.

Scrolling up loads older messages without moving the message the player was reading. While the player is reading history, new messages leave the scroll position in place and offer a way to jump to the latest messages. At the bottom of the feed, new messages come into view automatically.

Mockup M03   Questions Q03 Q05

R05 Sending text

The send arrow posts to the active tab. Empty and whitespace-only messages cannot be sent. The client and server use the same way to measure length and apply the same limit.

The server response indicates whether the message was accepted or rejected. A rejected message can be edited and sent again. When a response is lost, retrying uses the original operation so the other player does not get two copies.

Mockup M03 M05   Questions Q06 Q07

R06 Stickers

The sticker icon opens the sticker picker. The test cases assume that choosing a sticker sends it immediately to the active tab and leaves the text draft in place. Closing the picker without choosing sends nothing.

The server checks whether the sticker is available to the player. If its image fails to load, the feed keeps a placeholder and offers a retry.

Mockup M03 M05   Questions Q08

R07 Requesting and claiming energy

The test cases assume that players in the channel can see the card and the server checks claim eligibility for each player. An eligible player gets 50 energy from a card once. Whether the player who posted the request can claim from it still needs confirmation.

The button shows a pending state while the server responds. A successful claim, an already claimed card, an expired card, and a rejection are distinguishable. If the response is lost, the client checks the balance and card state against the server. The claim record and balance increase are committed together.

Mockup M04   Questions Q09 Q10 Q11

R08 Connection loss and account changes

Chat shows the connection loss and keeps the draft. On reconnect, it loads anything that arrived during the outage. For a send or claim with no response, the client checks the result or retries with the original operation ID.

An expired session cannot send a message or claim energy. After signing in with a different account, the previous player’s history, drafts, and events stay hidden. The current account receives updates through one subscription.

Mockup M01 M03 M04 M05   Questions Q07 Q12

R09 Text display and moderation

Chat renders another player’s name and message as plain text, including angle brackets. If the server rejects a message, the sender sees the reason and the recipient does not see the message.

Confirm the moderation rules, message rate limit, and how very long words wrap. To verify a rejection, check the sender’s screen, the recipient’s feed, and the server response if it is available.

Mockup M03 M05   Questions Q06 Q13

R10 Small screens and keyboard controls

With the on-screen keyboard open, the player can still send a message, switch tabs, and close chat. On a small screen and with enlarged text, controls do not overlap and the name and timestamp stay with their message.

If the game supports a keyboard and a screen reader, Tab follows a predictable order. Focus is visible and each icon is announced by its purpose.

Questions for the product team

Start by confirming who can claim energy and how often. The answers to Q09 through Q11 determine the expected results for the energy cases.

Q01 How do players open chat and a private tab?

What do the map pin, heart, shield, and icon next to the input open? How many private tabs can a player open, and can they still interact with the game outside the chat window?

Q02 Who can see channels and private messages?

Is the Café shared by the whole game, one server, or one location? What happens to history if a player leaves a channel or the other player blocks them?

Q03 When does the red dot clear?

Does opening the tab count, or does the player have to see the last message? If they read it on their phone, does the dot clear on their other device?

Q04 Who is counted as online?

Which players make up the 237? When does the count refresh, how long does a disconnected player count as online, and what does the counter show when offline?

Q05 How is chat history stored?

How long are older messages kept and how many load at a time? Which time zone and format should the date and time use?

Q06 What can players type and send?

What is the length limit and how are multi-code-point emoji counted? How should long words wrap? Are line breaks and surrounding spaces kept? When should Enter send a message, including during IME input?

Q07 What happens when the server does not respond?

When should an error appear, and how long can a retry reuse the original send operation? Can players queue a message while offline?

Q08 How do players send a sticker?

Does selecting a sticker send it right away, or does the player have to confirm? Are there paid packs? What appears if the picker is empty or fails to load?

Q09 Who can claim energy and how? · P0

How does a player create a request? Can the requester click “Claim” on their own card? Where does the energy come from, and how many players can claim from one request?

Q10 When does a request stop being usable? · P0

Is there an expiry, a daily limit, a balance cap, or a limit on recipients? If there is room for fewer than 50 units, does the player get the remainder or is the claim rejected?

Q11 What appears after a player clicks “Claim”? · P0

How does the UI distinguish a pending response from rejection, expiry, and an already successful claim? Where can the player check their final balance after losing connection?

Q12 What is kept after restarting?

Does the draft survive quitting the game? Can one account sign in on two devices? How quickly does chat catch up after reconnecting?

Q13 How does moderation work?

How many messages can be sent within one rate-limit window? What is shown when a message is rejected, and can players report or block someone from chat?

Q14 What should the UI be tested on?

Which devices, minimum window sizes, input methods, and scaling settings does the game support?

Test cases

The suite contains 34 cases, including 15 P0 cases. They were designed from the mockup and have not been run on a game build.

Window and tabs

CHAT-01 Open, close, and reopen chat P1

Rules R01

Preconditions
A is in the game and has never opened chat.
Steps
  1. Open chat.
  2. Use the window’s close button, then open chat again.
Expected result
The first visit shows the Café feed and message field. The close button hides the window. Reopening shows the same channel without duplicating messages.
CHAT-02 Close a private tab and reopen the conversation P1

Rules R01 R02

Preconditions
A has open conversations with B and C. The conversation with B already contains message m1.
Steps
  1. Open the conversation with B and click the close button on that tab.
  2. Reopen the conversation with B.
Expected result
Chat stays open and switches to the Café. C’s tab remains open. When A reopens the conversation with B, m1 appears once.
CHAT-03 Send drafts from two different tabs P0

Rules R02 R05

Preconditions
A has the Café and a private conversation with B open. B and C can both read the Café.
Steps
  1. Type “for B only” in the private tab and “for everyone in the Café” in the public channel. Switch tabs and check the draft in each one.
  2. Send the message from each tab. Check B’s and C’s feeds.
Expected result
Each tab kept its own draft. B sees “for B only” in the private chat and “for everyone in the Café” in the public channel. C sees only the public message.
CHAT-04 Check that an outside player cannot see a private chat P0

Rules R02

Preconditions
A and B have a private conversation containing m1. C is signed in under a separate account. The test environment supports separate read and send checks.
Steps
  1. Ask A to message B. Check C’s conversations and incoming events.
  2. Using C’s session, check how the server handles attempts to read A and B’s conversation history and send a message to it.
Expected result
C sees none of the conversation, its history, or A’s new message. The server rejects both operations from C. No message from C appears in A and B’s conversation.
CHAT-05 Switch tabs while history is loading P1

Rules R02 R04

Preconditions
A has access to two channels with different message histories. The test environment can delay responses.
Steps
  1. Open the first channel and hold its history response.
  2. Open the second channel. Once its messages are visible, release the delayed response.
  3. Send a message from the second channel.
Expected result
The second tab stays active. Messages from the first channel do not appear in it. The new message reaches the second channel.
CHAT-06 Revoke channel access while the player is reading it P0

Rules R01 R02

Preconditions
A is reading a restricted channel and has a draft in the message field. B will retain access.
Steps
  1. Remove A from the channel and check whether A can send the draft.
  2. Close and reopen chat. As B, check whether A’s text appeared.
Expected result
The restricted feed disappears for A. The draft is not posted. Reopening chat takes A to a channel they can access.

Test plan

Test data and environment

Prepare three accounts. A is the primary test player, B is their chat partner, and C is an outside player. Set up the Café, a second channel, and private chats between A and B and between A and C. The test environment should let you reset an energy balance and card or delay a specific server response.

Record the client version, accounts, timestamp, operation ID, actual result, and case status. If a message disappears or is duplicated, compare both players’ histories with the server record. For energy, capture the balances before and after and count the credit entries.

Priorities and release criteria

P0
Exposure of private messages, access control errors, lost or duplicate messages, and incorrect balances.
P1
Opening chat, sending text and stickers, history, notifications, and input limits.
P2
Reading older messages and retrying images that fail to load.

Start with CHAT-01, CHAT-03, CHAT-07, CHAT-14, CHAT-21, CHAT-23, and CHAT-31. Then run the remaining P0 cases, using two devices where needed. Before release, confirm the access and energy rules, pass the initial suite, and resolve any P0 defects.
